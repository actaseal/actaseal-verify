# actaseal-verify 1.0.2

Release notes. Not yet tagged or published when this file was written.

## What changed since 1.0.1

**A keyless check for packets: `verify.py --checkpoint HEX`.** When the
key that signed a receipt cannot be trusted or is not known to you
(rotated out, lost, never published to you), supply the hash of a ledger
event you already trust, obtained out of band. The packet then passes on
the chain alone, reported as `CHAIN_VERIFIED_KEY_UNKNOWN` and never as a
signature check, if that hash is in the packet's unbroken slice at or
after the receipt's ledger entry and an event under it records the
receipt's own hash. With a signature that verifies it is one more check.
A key or keyring you supply is never overridden by a checkpoint. New
failure codes: `CHECKPOINT_NOT_IN_SLICE`,
`CHECKPOINT_BEFORE_RECEIPT_ENTRY`, `CHECKPOINT_RECEIPT_NOT_COMMITTED`.

`verify_receipt.py` already had a `--checkpoint` for a bare receipt. Its
rule is unchanged and is weaker than the packet one: it requires the
checkpoint to be in the supplied slice, not that it comes after the
receipt's entry, and a bare receipt carries no record of its own hash in
the chain. Prefer the packet check when you have the packet.

**Comments and help text.** The source files described themselves by
pointing at files of the licensed product. They now describe each check
in terms of this repository and the standards it follows. One printed
note in `verify_receipt.py` changed for the same reason.

**A stricter Ed25519 check.** `verify.py` now refuses, by itself and before it asks
the cryptography library, an Ed25519 public key or a signature `R` that is a
small-order point, a mixed-order point (a prime-order point plus a torsion point:
L times it is not the identity) or a non-canonical encoding (a y coordinate of at
least p). The library underneath accepts some of these, and two verifiers can then
disagree about the same signature. A receipt, a hybrid receipt's Ed25519 half or a
signed tree head that fails this reports `RECEIPT_SIGNATURE_INVALID` (or a failed
tree-head check) like any other bad signature. No real signer produces such a key
or an `R` like that, so no honest receipt is affected; every conformance vector
and demo packet gives the same output as before.

**The settlement anchor is bound.** Reported on the IETF SCITT list on 17
November 2026 by Bassem Kudsi: in an anchored packet, the anchor's content
could be edited, with `anchor_hash` recomputed, or the whole block replaced
with `{"status": "SETTLEMENT_UNANCHORED"}`, and the packet still printed
`VERIFIED`. Nothing signed covered the anchor, and its `mandate_hash` was
not compared with the receipt's. The receipt is signed before the money
settles, so it cannot cover the anchor. Now:

- an anchored block's `anchor.mandate_hash` must equal the receipt's
  (`SETTLEMENT_ANCHOR_UNLINKED`);
- an anchored block may carry `anchor_signature`
  (`{"algorithm": "ed25519", "public_key_hex", "signature_hex"}`), a
  signature over the canonical bytes of `anchor` by the party that saw
  settlement. A bad one fails (`SETTLEMENT_ANCHOR_SIGNATURE_INVALID`);
- `--settlement-public-key HEX` pins that party's key
  (`SETTLEMENT_ANCHOR_KEY_MISMATCH`), and with it an unsigned anchor, or a
  packet stating `SETTLEMENT_UNANCHORED`, fails
  (`SETTLEMENT_ANCHOR_UNSIGNED`).

What a packet alone still cannot show is printed with every `VERIFIED`
result, never passed off as checked: an anchor without a signature
(`SETTLEMENT_ANCHOR_UNSIGNED`); that a packet stating nothing settled had
its settlement removed (`SETTLEMENT_STATUS_UNSIGNED`; look for a registered
settlement statement for the action); and that `acquisition.json`,
`custody.json` and `authentication.json` are not signed, so only their
fields cross-checked against the receipt and ledger slice are verified
(`NOT_COVERED_BY_SIGNATURE`). `tests/test_settlement_anchor_binding_v1.py`
edits every field of the anchored demo packet, one at a time, and requires
each edit to fail or to sit in a file that note names.

**The continuity checkpoint's key can be pinned.** Found in a
self-review on 22 November 2026, while checking the RFC 9942 tree-size
observation Bassem Kudsi posted to the IETF SCITT list. When a packet
carries `checkpoint.json`, its signed tree head was checked only against
the public key shipped in that same file, so anyone could build a tree
holding the receipt, sign it with their own key, and the packet still
printed `VERIFIED` with no word about the key. The tree size itself was
already bound: it is inside the signed tree head, and the inclusion
proof's size must match it. Now:

- `--sth-public-key HEX` also applies to a dispute packet: the
  checkpoint's key must equal it (`CHECKPOINT_KEY_MISMATCH`), and giving
  it for a packet with no `checkpoint.json` fails (`CHECKPOINT_MISSING`);
- without it, every `VERIFIED` result for a packet with a checkpoint
  prints `CHECKPOINT_KEY_NOT_PINNED` and the key that was used.
- a `consistency_proof.json` must end at the signed tree head's size and
  root (`CONSISTENCY_PROOF_NOT_AT_SIGNED_HEAD`). Before, any
  self-consistent proof between made-up roots passed. Its old root is
  signed by nothing in the packet, so `VERIFIED` prints it as
  `CONSISTENCY_OLD_ROOT_NOT_CHECKED` for you to compare with a checkpoint
  you trust.

**No check was removed or loosened.** Apart from `--checkpoint`, the stricter
Ed25519 check, the settlement anchor checks and the checkpoint key pin above, `verify.py` is the same program as in 1.0.1 with comments and
docstrings set aside, and every output on every conformance vector and demo packet
gives the same verdict. Every `VERIFIED` output gains the notes above, and
the two verifier-digest vectors print this file's own hash.

## If you hold packets made before this release

A packet may pin the verifier it was shipped with (`verifier_sha256` in
`manifest.json`). That pin is over the verifier's body, comments
included, so it names one exact `verify.py`:

| | |
|---|---|
| `verify.py` body digest in 1.0.2 (the value a packet pins) | `35c0dfa42da389013a1813679e6565e403aebb947ac5f912d9947767a7a15a94` |
| `verify.py` file SHA-256 in 1.0.2 | `be1044d7496f640ffaf48d5f1cdb4d3c2e66d818d28fec2140323afa0f00835d` |

Checking a packet that pins an earlier body with this `verify.py`
reports `VERIFIER_DIGEST_MISMATCH`. That is the pin doing its job, not
damage to the packet. Check such a packet with the `verify.py` it
carries, whose hash is the one it pins. The packet format itself is
unchanged: `VERIFIER_SUPPORTS_ROOT_VERSIONS` is still `("v1", "v2")`.

## Conformance vectors

- New group `vectors/packet_checkpoint/` (six cases) with its own runner.
- `vectors/verifier_digest_valid/` is regenerated for this body. It had
  been left pinned to an earlier body when `--help` was added, so
  `conformance/test_conformance.py` was failing on `main` from then
  until this release.
- Every anchored vector's `manifest.json` now carries an `anchor_signature`,
  by a key derived from that vector's fixed receipt key, so regeneration
  stays byte-identical. Every other vector file is unchanged.
